# 技术报告 — redis-lite

> 这份报告是简历项目的**核心交付物**。简历上写一行项目名没人会点，但写
> 「13.6 万 QPS / P99 88µs / 97 个单测 / kill -9 恢复无损，技术报告见 GitHub」
> 面试官会主动问。
>
> 报告的重点不是"我做了什么"，而是**"我为什么这么做、放弃了什么、缺口在哪"**。

---

## 1. 问题定义

实现一个单机高性能 KV 服务，要求：

1. 兼容 RESP2 协议（让 `redis-cli` 能直接连，便于验证与演示）
2. 支持字符串与有序集合两类数据结构
3. 崩溃后数据可恢复，且**恢复到一致状态**（不能出现半个命令）
4. 性能可量化，且能说清瓶颈在哪

**明确的非目标**：集群、主从复制、事务、发布订阅。
理由：这些是"分布式"命题，而本项目的命题是"单机极致"。
混在一起会两边都讲不深。

## 2. 架构

### 2.1 分层与依赖方向

```
app  →  protocol  →  net  →  storage  →  common
```

依赖严格单向。三个具体收益（都是实测的，不是理论）：

- **协议层可独立测试**：`RespParser` 不认识 socket，所以能写"逐字节喂入"的
  半包测试 —— 这类测试在网络层里是写不出来的。
- **AOF 恢复复用线上路径**：AOF 存的就是 RESP 命令流，恢复时用同一个
  `RespParser` + 同一个 `Dispatcher`。**恢复路径与在线路径共享代码**，
  消灭了一整类"恢复时行为不一致"的 bug。
- **存储结构可替换**：ZSet 从跳表换成 `std::set` 时，命令层一行未改。

### 2.2 线程模型：主从 Reactor

```
                  ┌──────────────┐
   客户端 ────────▶│  Main Loop   │  只做 accept
                  │  (1 线程)    │  新连接 round-robin 分发
                  └──────┬───────┘
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
    ┌──────────┐   ┌──────────┐   ┌──────────┐
    │ SubLoop 0│   │ SubLoop 1│   │ SubLoop N│  读写 + 命令执行
    │  epoll ET│   │  epoll ET│   │  epoll ET│  每连接固定亲和
    └────┬─────┘   └────┬─────┘   └────┬─────┘
         └──────────────┼──────────────┘
                        ▼
            ┌────────────────────────┐
            │  Store（64 分片）      │  每分片独立 mutex
            └───────────┬────────────┘
                        ▼
            ┌────────────────────────┐
            │  后台线程              │  每 100ms：过期采样 + AOF fsync
            └────────────────────────┘
```

**为什么是 N+1 个事件循环线程，而不是"一个 epoll 线程 + 线程池"**：
后者需要把连接状态在 IO 线程与工作线程之间传递，要么加锁、要么做
owner 迁移，两者都会引入复杂度。one-loop-per-thread 让**连接对象完全不需要锁**
（生命周期内只被一个线程触碰），把并发复杂度限制在存储层的分片锁这一处。

### 2.3 关键实现细节

**① epoll 边缘触发（ET）的读循环**

ET 只在状态变化时通知一次。若只 `recv` 一次就返回，剩余字节会永远留在
内核缓冲里而 epoll 不再通知 —— 连接静默挂死。所以必须**循环读到 EAGAIN**。

代码位置：`src/connection.cpp` 的 `HandleRead()`。

**② 写事件的延迟注册**

空闲连接不订阅 `EPOLLOUT`。若一直订阅，epoll 会持续报告可写，造成
100% CPU 空转 —— 这是自研 Reactor 最常见的性能事故。

代码位置：`src/connection.cpp` 的 `EnableWriteIfNeeded()` / `DisableWriteIfIdle()`。

**③ accept 必须循环 + EMFILE 处理**

漏掉循环 accept = 永久积压连接。
`EMFILE`（fd 用尽）时必须牺牲一条连接换取队列排空，否则
「队列非空 → epoll 持续可读 → 忙等」会烧满 CPU。

代码位置：`src/listener.cpp` 的 `OnReadable()` / `HandleAcceptError()`。

**④ 存储分片锁**

64 个分片，每分片独立 `std::mutex`。不同分片的操作真正并行，
锁冲突概率降到约 1/64。相比"一把全局大锁"，这是多核下的必要条件。

代码位置：`src/store.cpp`。

**⑤ TTL 的单调时钟**

过期时刻用**单调时钟的绝对毫秒**存储（`CLOCK_MONOTONIC` /
`QueryPerformanceCounter`），而不是墙上时钟。这样系统时间被修改
（NTP 校正、手动改时间）不会导致 TTL 错乱。

惰性过期（读路径遇到就删）+ 主动过期（后台每 100ms 采样 20 个）双管齐下，
与 Redis 原始设计一致。

**⑥ AOF 的绝对时刻转换**

`EXPIRE key 100` 落盘时转成 `PEXPIREAT key <绝对毫秒>`。
若原样落 `EXPIRE`，重放时相对时间会被**重新计算**，语义就变了。

**⑦ FLUSHALL 的 AOF 截断重写**

`FLUSHALL` 会把 AOF 整体重写为一条 `FLUSHALL` 命令。
若不处理，重启后旧数据会"复活" —— 这是很多自制 KV 的隐藏 bug。

## 3. 数据结构与复杂度

### 3.1 字符串值：三态编码

| 编码 | 适用场景 | 收益 |
|---|---|---|
| `kString` | 一般字符串 | — |
| `kInt` | 可解析为 int64 的值 | 省内存；`INCR` 免去字符串解析 |
| `kZSet` | 有序集合 | 见下 |

对外**统一**表现为 string（`TYPE` 返回 `string`），编码是内部实现细节。
`INCR` 对 `kString` 编码的 `"41"` 也能正确自增到 42。

### 3.2 有序集合：双索引

ZSET 需要同时满足三类复杂度要求，**没有单一数据结构能全部做到最优**：

```
index_  : unordered_map<member, score>    ZSCORE / ZINCRBY   期望 O(1)
sorted_ : std::set<pair<score, member>>   范围查询 + 有序性    O(log N + M)
```

排序键是 `(score, member)` 的字典序全序 —— score 相同时按 member 排序。
这个全序与 Redis 一致，是 `ZRANGE` 结果稳定可预期的基础。

**写路径的一致性要求**：任何修改必须同步两个索引。
`score` 变化时不能原地改（`std::set` 的键是 const，且改键会破坏红黑树有序性），
必须「删旧 + 插新」。

### 3.3 复杂度对照表（含与 Redis 的差距）

| 操作 | 本实现 | Redis | 差距原因 |
|---|---|---|---|
| `GET` / `SET` | 期望 O(1) | O(1) | — |
| `DEL` / `EXISTS` | 期望 O(1) | O(1) | — |
| `INCR` | 期望 O(1) | O(1) | — |
| `ZADD` | 期望 O(log N) | 期望 O(log N) | — |
| `ZSCORE` | 期望 O(1) | O(1) | — |
| `ZCARD` | O(1) | O(1) | — |
| `ZRANGE` | O(log N + M) | O(log N + M) | — |
| `ZRANGEBYSCORE` | O(log N + M) | O(log N + M) | — |
| **`ZRANK`** | **O(log N)** | **O(log N)** | 已对齐，见 3.4 |
| `KEYS` | O(N) | O(N) | — |

### 3.4 ZRANK：一个被攻克又闭环的复杂度缺口

**结论先说**：`ZRANK` 现在是 **O(log N)**，并附实测证据（3.4.3）。

#### 3.4.1 曾经的困境

第一版用 `std::set` 做有序索引，`ZRANK` 只能 `std::distance(begin, it)`，
即 O(rank) ≈ O(N/2)。要降到 O(log N) 必须换**带 span 的跳表**
（`span` 记录每条前向指针跨过多少节点，搜索路径上累加即得排名）。

我实现了它，但 `span` 的**增量更新**在多种层数分布下反复出错：
错误表现是「rank 时对时错」——同一个测试，换个层数就换一种错法。

连续调试 **11 轮未收敛**后，我在交付压力下做了取舍：

> **选择「保证正确 + 明确记录缺口」，而不是「带着未验证的复杂度上线」。**

当时把缺口、影响面、补齐路径全部写进了报告，把跳表代码移出构建，
用 `std::set` 保证交付。**这个决定本身没有错** —— 错的是当时的方法。

#### 3.4.2 后来是怎么解决的

两周后重新攻克，改变了两件事：

**① 把 span 的定义收敛成唯一一条式子**

之前我对 span 的理解在「距离」和「覆盖数」之间摇摆，两种理解在单点上
都能自圆其说，但差 1，且**每一层的偏差不同**。现在只保留一条：

```
span[i](x) == rank(x->forward[i]) - rank(x)
```

其余全部由它推导（包括"后继为空时视作虚拟表尾 `size+1`"）。
定义唯一之后，代码里不再有需要"分类讨论"的地方。

**② 停止"改一版跑一次"，改用穷举测试**

这是真正的转折点。我写了一个可注入层数生成器的钩子，然后枚举
**「N 个元素各自层数」的全部组合**（N=4/6/7 配 maxLevel=3、N=5 配 maxLevel=5，
共 **6122 组**），每组逐步插入并校验全部不变式。

第一次运行就精确定位到：

```
n=4 maxLevel=3 code=1 step=1: Rank(m1) = 2, expected 1
levels = 2 1 1 1
```

**根因**：累加排名时读错了字段 ——

```cpp
rank += x->forward[i]->span[i];   // ❌ 读的是【后继】的 span
rank += x->span[i];               // ✅ 按定义应读【自己】的 span
```

而且这个错误在 **3 处复制**（插入搜索、`ZRANK`、`ZRANGE` 的定位）。

**为什么这么难发现**：第 0 层每个节点的 span 都是 1，所以
`x->span[0] == x->forward[0]->span[0]` —— **纯单层场景永远正确**，
只有跨层时才偏。这完美解释了"时对时错"：手工挑的用例恰好都落在单层路径上。

#### 3.4.3 实测证据

`tools/bench_zrank.cc` 在多个规模上测同一操作（复杂度是渐进行为，
必须看**增长趋势**而不是单个规模的绝对值）：

| N | ZRANK 单次 | N 增长 | ZRANK 耗时增长 |
|---|---|---|---|
| 1,000 | 0.257 µs | 1× | 1× |
| 10,000 | 0.528 µs | 10× | 2.05× |
| 100,000 | 1.956 µs | 100× | 7.60× |
| 1,000,000 | 4.230 µs | 1000× | **16.4×** |

**规模扩大 1000 倍，耗时只增长 16.4 倍** —— 明确的亚线性。
若是 O(N)，100 万规模应约 257 µs（实测慢 60 倍）。

顺带验证了 ZADD 也是亚线性（0.76 µs → 4.02 µs，1000× 规模下增长 5.3×）。

#### 3.4.4 这个故事在面试里怎么讲

比"我实现了一个跳表"更有价值的是这个完整的闭环：

1. **先做了诚实取舍**：调不通就记录缺口、移出构建、保证交付
2. **后来用对方法攻克**：不再靠人工构造用例 + 手工推演，
   而是**让机器穷举**，自己指出哪一组开始错
3. **根因是一个字段混淆**，且在 3 处复制；它之所以隐蔽，
   是因为第 0 层的巧合掩盖了错误

**可迁移的结论**：调试复杂数据结构时，
「先定义正确性（不变式自检），再用穷举代替人工挑用例」
比任何具体技巧都有效。

完整记录见 `docs/IMPLEMENTATION_LOG.md`。

## 4. 持久化与崩溃一致性

### 4.1 设计

```
写命令 → 解析 → 执行 → 追加到 AOF 缓冲 → 按策略落盘
                            │
                            ├─ always  : 每条命令 fwrite + fsync
                            ├─ everysec: 后台每 100ms 批量 fsync（默认）
                            └─ no      : 只交给 OS
```

**为什么 AOF 用 RESP 而不是自定义格式**：这样恢复时能复用线上同一个解析器，
不需要维护第二套解析逻辑。「在线路径与恢复路径共享代码」是消灭一类 bug
的有效手段。

**有界缓冲**：缓冲超过 4MB 时强制同步落盘，防止高频写入把内存吃光。

### 4.2 已验证的一致性保证

| 场景 | 保证 | 验证方式 |
|---|---|---|
| 进程崩溃（`kill -9`） | 不丢已 fsync 的数据；TTL 语义不变 | 实测：写 ZSET + TTL → 强杀 → 重启 → 数据与 TTL 全部正确 |
| AOF 尾部半条命令 | 截断到最后一个完整命令，**不报错启动** | 单测 `aof_truncates_incomplete_tail` |
| AOF 尾部乱码 | 截断并告警，好数据保留 | 单测 `aof_truncates_on_protocol_error_in_tail` |
| 二进制 value（含 `\0`） | 无损往返 | 单测 `aof_preserves_binary_values` |
| `SET NX` 失败 | **不写 AOF** | 单测 `aof_nx_failure_is_not_persisted` |
| `EXPIRE` 重放 | 转 `PEXPIREAT` 绝对时刻 | 单测 `aof_expire_persisted_as_absolute_time` |

**实测恢复日志**（`kill -9` 后重启）：

```
[INFO] AOF opened: path=zset_test.aof size=278 policy=everysec
[INFO] AOF loaded: zset_test.aof -> 7 commands
[INFO] AOF replay done: 7 commands
```

恢复后 `ZRANGE` / `ZCARD` / `ZSCORE` / `ZRANK` / `GET` / `TTL` 全部正确，
被 `ZREM` 删除的成员没有复活。

## 5. 测试策略

**97 用例 / 3348 断言**，四个套件：

| 套件 | 用例数 | 重点 |
|---|---|---|
| `test_resp.cc` | 25 | 增量解析的半包 / 粘包 / 协议错误 / glob / 整数解析边界 |
| `test_store.cc` | 27 | NX/XX 语义、TTL 三态、惰性过期、并发正确性 |
| `test_aof.cc` | 10 | 崩溃恢复、尾部截断、二进制安全、端到端重放 |
| `test_zset.cc` | 24 | 双索引一致性、随机交叉验证、score 格式化往返 |

### 三个值得单独说的测试手法

**① 半包测试：逐字节喂入**

```cpp
for (size_t i = 0; i + 1 < full.size(); ++i) {
    p.Append(full.data() + i, 1);
    RL_CHECK_MSG(!p.Next(&args), "parser must not complete before all bytes arrive");
    RL_CHECK_EQ(p.buffered(), i + 1);   // 未完成时游标绝不能前移
}
```

这抓出了一个真实 bug：解析中途数据不足时，已 `std::move` 进 `args` 的元素
没有回滚，调用方会以为拿到了半条命令。

**② 并发 INCR 无丢失**

8 线程 × 500 次并发自增同一个 key，最终值必须精确等于 4000。
这是"分片内互斥是否真的生效"的直接验证 —— 若锁写错，这里会随机失败。

**③ 随机交叉验证（最有价值）**

ZSet 的随机测试：3000 次随机 `Add`/`Remove`/`IncrBy`，每 100 步与
"暴力重建的参考实现"全量比对 size、全序、每个元素的 rank 与 score。

**为什么必须这么做**：双索引不一致的 bug 不会崩溃、不会报错，
只会让某个元素"ZSCORE 查得到但 ZRANGE 看不到"。手工挑用例根本抓不住。

配套的随机数用**自实现的 LCG** 而不是 `std::rand` —— 后者的实现跨平台不同，
会让失败无法复现。

## 6. 性能

### 6.1 测试环境

| 项 | 值 |
|---|---|
| **服务端环境** | **Ubuntu 22.04.4 LTS，x86_64，VMware 虚拟机** |
| **CPU** | **2 核** |
| 编译器 | g++ 11.4.0，`-O2`，`-Wall -Wextra`（**0 告警**） |
| **IO 后端** | **epoll 边缘触发**（启动日志确认 `edge_trigger=1`） |
| 客户端 | 自研 `tools/bench.cc`，6 并发连接 |
| 命令 | `SET`，value 64 字节，keyspace 10000 |
| 请求数 | 100000 |

**测试环境必须诚实标注**：这是 **2 核虚拟机**，不是裸机。
虚拟化有 CPU 开销，2 核也限制了并行度上限。
换裸机（尤其更多核）数字会显著不同，但**本报告的所有结论都是相对的、
与核数无关的**（见 6.3）。

### 6.2 完整压测矩阵

`threads`（Sub Reactor 数）× `pipeline`（流水线深度）：

| threads \ pipeline | 1 | 16 | 64 |
|---|---|---|---|
| **1** | 16,020 ops/s<br>P99 1120 µs | 152,889 ops/s<br>P99 99.9 µs | 218,426 ops/s<br>P99 46.8 µs |
| **2** | 23,579 ops/s<br>P99 1046 µs | 262,112 ops/s<br>P99 48.1 µs | **297,942 ops/s<br>P99 46.8 µs** |
| **4** | 23,511 ops/s<br>P99 1040 µs | 228,541 ops/s<br>P99 58.7 µs | 289,021 ops/s<br>P99 43.2 µs |

**最优配置**：`threads=2, pipeline=64` → **297,942 ops/s，P50 15.8µs，P99 46.8µs，P99.9 56.8µs**

复现实验：`scripts/bench_matrix.sh`（一条命令跑完整矩阵）。

### 6.3 三条结论（这才是数据的价值）

**结论一：pipeline 是决定性的，threads 不是。**

单线程下 pipeline 从 1 提到 64，吞吐从 **1.6 万涨到 21.8 万，13.6 倍**。

原因：`pipeline=1` 时，每个请求都要经历一次完整的
「客户端写 → 服务端 epoll 唤醒 → 处理 → 回写 → 客户端唤醒」往返，
瓶颈是**往返延迟与上下文切换**，而不是服务端处理能力。
放大 pipeline 让服务端一次拿到一批命令，把「每请求一次 syscall」
摊薄成「每批一次 syscall」—— 这正好命中 epoll ET 的读循环设计
（一次可读事件把内核缓冲读干净）。

**结论二：线程数超过物理核数没有收益，甚至会略降。**

2 核 VM 上：2 线程 297,942，4 线程 289,021（**降了 3%**）。

这与预期一致：Sub Reactor 数超过核心数只会增加调度与缓存失效开销。
**生产环境应该把 `--threads` 设为核心数**，而不是拍脑袋给个大值。

**结论三：低 pipeline 下尾延迟极差（P99 1.1ms vs 46.8µs，差 23 倍）。**

`pipeline=1` 的 P99 是 1120µs，而 `pipeline=64` 只有 46.8µs。
这说明高尾延迟的来源不是服务端处理慢（服务端单命令处理只要几 µs），
而是**排队**：客户端并发 6 个连接争抢服务端唤醒时机会产生长尾。

**面试价值**：这条能直接回答"你的服务尾延迟为什么高"——
先看是不是客户端没做 pipeline，再谈服务端优化。
很多人在没排除这个因素前就开始优化服务端，方向就错了。

### 6.4 perf 热点定位

`perf record -F 999 -p <server>` 采样 6 秒（约 30 万请求）：

| 占比 | 符号 | 解读 |
|---|---|---|
| 3.05% | `__memmove_avx_unaligned_erms` | 内存拷贝 —— 缓冲区间搬运 |
| 1.53% | `_Hashtable::find`（`unordered_map<string, Entry>`） | **存储层哈希查找** |
| 0.76% | `pthread_mutex_lock`（`rl-bg` 后台线程） | 过期扫描与 AOF 刷盘 |
| 0.76% | `__memcmp_avx2_movbe` | key 比较（哈希碰撞时的字符串比对） |
| 0.76% | `epoll_wait` | 事件等待本身 |
| 0.76% | `Connection::HandleWrite` | 写路径 |
| 0.76% | `Dispatcher::Execute` | 命令分派 |
| 0.76% | `Store::Set` | 存储写入 |

**关键观察：没有单一热点超过 3.1%，profile 非常扁平。**

这是**健康**的信号，说明没有明显的性能坑（例如某处 O(n) 扫描、
或锁竞争导致的 `futex` 尖峰）。同时它说明了一件事：

> **当前吞吐瓶颈不在 CPU 上，而在 syscall 与内存拷贝上**
> （`memmove` 第一、`epoll_wait` 可见、`HandleWrite` 可见）。

**优化方向（按此 profile 判断，而不是凭直觉）**：
1. **减少内存拷贝**：`memmove` 占 3% —— 输入缓冲的 `std::string` 追加、
   输出队列的构建都有优化空间（例如用环形缓冲 + `writev` 直接引用）
2. **合并 syscall**：用 `writev` 把多个回复段一次写出，替代多次 `send`
3. **哈希查找**：`_Hashtable::find` 占 1.5% —— 换更快的哈希、
   或用 `string_view` 避免临时 `std::string` 构造
4. 锁竞争**不是**当前瓶颈（`pthread_mutex_lock` 只占 0.76%，
   且集中在后台线程），说明 64 分片的设计是够用的

**注意这里的方法论**：先 profile，再决定优化什么。
上面前 3 条如果凭直觉猜，很可能猜错顺序。

### 6.5 与 Windows 基线的对比

| 后端 | 吞吐（pipeline 16, 8 连接） | P99 |
|---|---|---|
| Windows + `select`（功能基线） | 136,405 ops/s | 88.2 µs |
| Linux + `epoll ET`（本文数据） | 262,112 ops/s（6 连接） | 48.1 µs |

**但这个对比不完全公平**，因为客户端连接数、总请求数、操作系统都不同。
诚实的说法是：**两条数据不能直接相减**。Linux/epoll 在架构上更优
（`select` 有 `FD_SETSIZE` 上限和 O(n) 就绪扫描），但具体差值需要
在同一压测参数下重跑才能得出。这是尚未完成的验证项。

## 8. 面试常见追问与回答要点

**Q：为什么 ET 而不是 LT？**
ET 把"一个 segment 一次唤醒"降到"一批数据一次唤醒"，在 pipeline 场景下
syscall 次数显著减少。代价是实现复杂度：必须循环读到 `EAGAIN`，
且 accept 也必须循环。LT 更简单但每个可读事件都会唤醒。

**Q：分片锁为什么是 64 片？**
2 的幂便于用位与代替取模。64 是在"锁冲突概率"与"内存/缓存局部性"之间的折中：
片数越多冲突越少，但每片的哈希表更小、缓存命中率可能下降。
这个值应该用压测扫描确定，目前是经验值。

**Q：为什么 AOF 用 RESP 而不是二进制格式？**
为了复用线上同一个解析器。代价是体积比二进制大约 2 倍，
但换来的是"在线路径与恢复路径共享代码"。

**Q：ZRANK 为什么不是 O(log N)？**（✅ 这个缺口已经补上了，见 3.4）
如果按第一版回答：用 `std::set` 无排名信息，带 span 的跳表我实现了但没调通，
在交付压力下选择了正确性优先，并给出补齐路径。
**现在可以给出的完整回答**：跳表已落地，ZRANK 是 O(log N)，
并用多规模实测数据证明（1000× 规模下耗时仅增 16.4×）。
更值得讲的是**怎么攻克的**：曾经连续 11 轮没收敛，
根因是累加排名时读错了字段（读了后继的 span 而非自己的 span），
且这个错误在 3 处复制；它之所以隐蔽，是因为第 0 层每个节点的 span
都是 1，恰好掩盖了错误 —— 纯单层场景全对，只有跨层才偏。
最后靠**穷举层数组合的测试**（6122 组）第一次运行就定位。
这个故事体现的是：**取舍的诚实 + 方法的可迁移**。

**Q：为什么跳表而不是红黑树？**
`ZRANK` 需要按排名查询。红黑树节点不知道自己的排名，要支持它必须额外
维护 size 域并在每次旋转时修正 —— 实现复杂且容易错。
跳表把「跨过多少节点」直接存在每条指针旁（span），沿途累加即得排名，
天然支持；且范围查询、并发友好性都更好。Redis 的 ZSET 同样选跳表。

**Q：如果 QPS 要再翻一倍，你会先动哪里？**
按当前信息的判断顺序：
1. 先做 `perf` 定位（不要凭直觉优化）
2. 大概率是减少 syscall：用 `writev` 合并输出、批量 accept
3. 然后是存储层：目前每命令一次分片加锁，可考虑批量命令合并加锁
4. 再往后才是无锁化 —— 但无锁的复杂度通常不值得，除非profile证明锁是瓶颈

**注意第 1 条**：这个回答的价值在于"先测量再优化"的方法论，
而不是具体优化手段。
